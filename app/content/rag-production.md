# RAG（Retrieval-Augmented Generation，检索增强生成）完整知识体系与工程实践

## 1. RAG 基础

### 1.1 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将外部知识检索与大语言模型（LLM）生成能力结合起来的 AI 应用架构。

大语言模型擅长理解和生成语言，但模型参数中的知识有限，也无法天然访问企业私有资料。RAG 在回答之前先从外部知识库中查找相关内容，再把检索结果作为上下文交给模型。

传统 LLM 主要依赖模型参数中的知识，而 RAG 在生成前增加检索阶段：

```text
用户问题
   ↓
检索器查询知识库
   ↓
返回相关文档切片
   ↓
构建上下文
   ↓
大语言模型生成回答
   ↓
答案与来源引用
```

RAG 的核心思想：

> 先检索可靠知识，再让模型基于知识生成答案。

例如，用户询问“产品 A 3.0 如何升级”。通用模型可能不知道企业内部的升级步骤，RAG 系统会先找到《产品 A 3.0 升级指南》，再根据文档生成答案并标注来源。

RAG 并不是一种新的大语言模型，也不等于向量数据库。它是一套完整流程，通常包含文档解析、文档切片、向量化、索引、检索、重排序、上下文构建、答案生成和效果评测。

------------------------------------------------------------------------

## 2. 为什么需要 RAG

### 2.1 解决模型知识更新滞后问题

大语言模型（LLM）的知识主要来源于训练数据，而训练数据存在时间截止点。模型无法自动获取训练完成后产生的新知识。

例如：

-   企业内部文档
-   产品资料
-   技术文档
-   最新业务数据

这些信息通常不会直接存在于模型参数中。

RAG 通过引入外部知识库，在用户提问后先检索相关的最新资料，再将检索结果作为上下文（Context）提供给模型，使模型能够基于这些资料生成回答。

需要注意：

> RAG 并不会改变模型参数或模型本身已有的知识，而是在推理阶段扩展模型可访问的信息来源，以弥补训练数据时间截止带来的知识更新滞后问题。

------------------------------------------------------------------------

### 2.2 企业私有知识增强

企业知识通常不在通用模型训练数据中。

例如：

-   API 文档
-   部署规范
-   产品手册
-   代码仓库

通过 RAG 可以在不重新训练大模型的情况下，让模型在推理阶段访问这些资料。

例如，企业客服机器人可以检索产品手册和售后政策；研发助手可以检索 API 文档、部署规范和故障处理记录。

企业场景还需要注意权限控制。用户只能检索其有权访问的文档，不能把全部资料召回后再让模型判断是否可以展示。

------------------------------------------------------------------------

### 2.3 降低幻觉

幻觉是指模型生成看似合理、实际没有依据或不正确的内容。RAG 通过检索真实资料作为上下文，为模型提供可参考的证据。

降低幻觉通常需要同时做到：

-   检索结果与问题相关；
-   提示词要求模型基于资料回答；
-   找不到可靠资料时允许拒答；
-   返回来源、页码或文档链接，便于核验。

但需要注意：

> RAG 不能完全消除幻觉，检索错误仍可能导致错误回答。

如果知识库本身有错误、检索到了无关内容，或者模型没有遵循上下文，最终答案仍可能不正确。因此 RAG 必须同时评测检索质量和生成质量。

------------------------------------------------------------------------

# 3. RAG 与其他技术区别

## 3.1 RAG vs 微调（Fine-tuning）

RAG 和微调都能改善模型表现，但解决的问题不同。

  对比项       RAG                                  微调（Fine-tuning）
  ------------ ------------------------------------ ------------------------------------
  核心目标     补充模型可访问的知识                 调整模型的行为、风格或任务能力
  数据使用     推理时检索外部知识                   训练时使用样本更新模型参数
  更新方式     更新知识库并重建相关索引             准备训练数据并重新训练或继续训练
  可追溯性     可以返回文档来源                     模型参数中的知识通常难以直接追溯
  适合场景     企业知识库、最新资料、私有文档       固定格式、特定风格、分类和专业任务
  主要成本     检索系统、向量存储和在线调用成本     数据标注、训练、验证和模型维护成本

简单理解：

> RAG 主要解决“模型不知道什么”，微调主要解决“模型应该怎样回答或执行任务”。

两者并不冲突。实际项目可以先通过微调让模型掌握稳定的行为模式，再通过 RAG 提供持续更新的业务知识。

------------------------------------------------------------------------

## 3.2 RAG、记忆与工具（RAG vs Memory vs Tool）

  能力               主要作用             解决的问题                 典型场景
  ------------------ -------------------- -------------------------- ----------------------------------
  RAG                检索并补充外部知识   模型缺少最新或私有知识     查询产品文档、技术规范、企业知识库
  记忆（Memory）     保存和恢复历史状态   模型无法持续记住交互信息   保存用户偏好、历史对话和任务进度
  工具（Tool）       访问系统并执行动作   模型无法直接操作外部系统   查询数据库、调用接口、发送消息

在智能体（Agent）系统中三者通常组合使用：RAG 负责补充知识，Memory 负责延续状态，Tool 负责执行动作。

------------------------------------------------------------------------

# 4. RAG 整体架构

完整 RAG 系统一般分为离线知识构建和在线问答两个阶段。

## 4.1 离线知识构建流程（Offline Pipeline）

```text
原始文档
   ↓
解析与清洗
   ↓
文档切片
   ↓
补充元数据
   ↓
生成向量
   ↓
写入向量数据库
   ↓
建立索引
```

离线阶段负责将 PDF、Word、网页、数据库记录等原始资料转换为可检索的知识。

各环节的作用：

-   **解析**：提取正文、标题、表格、页码和其他结构信息；
-   **清洗**：去除页眉页脚、乱码、重复内容等噪声；
-   **切片**：把长文档拆成适合检索的知识单元；
-   **元数据**：记录来源、版本、部门、权限和更新时间；
-   **向量化**：将文本转换为可以计算语义距离的向量；
-   **索引**：提高大规模向量检索速度。

这个阶段通常在文档新增、修改或删除时触发，不需要在每次用户提问时重新执行。

------------------------------------------------------------------------

## 4.2 在线问答流程（Online Pipeline）

```text
用户问题
   ↓
问题理解与改写
   ↓
权限和元数据过滤
   ↓
候选文档检索
   ↓
重排序
   ↓
上下文构建
   ↓
大语言模型生成
   ↓
答案、引用与拒答判断
```

在线阶段发生在用户提问之后：

1.  系统理解问题，必要时补全指代或改写查询；
2.  根据用户身份、部门和版本等条件过滤可检索范围；
3.  使用向量检索、BM25 或混合检索召回候选切片；
4.  使用重排序模型提升最相关内容的排名；
5.  对结果去重、排序并控制长度，形成上下文；
6.  大语言模型基于问题和上下文生成答案；
7.  系统返回来源引用；如果没有可靠资料，则给出明确的无答案提示。

生产系统还需要记录每一步的耗时、候选结果和得分，方便定位问题发生在检索阶段还是生成阶段。

------------------------------------------------------------------------

# 5. 文档解析与知识库构建

## 5.1 数据来源

常见数据：

-   PDF
-   Markdown
-   Word
-   PPT
-   HTML
-   数据库
-   代码仓库

不同来源的解析难点不同：

  数据类型       常见难点                               处理重点
  -------------- -------------------------------------- --------------------------------
  PDF            阅读顺序、页眉页脚、扫描件和复杂表格   版面解析、OCR、页码和表格结构
  Word/PPT       标题层级、文本框、图片和备注           保留章节、页面及对象关系
  Markdown/HTML  导航、广告、代码块和链接               清理模板噪声并保留语义结构
  数据库         多表关系、字段含义和数据权限           构造可读文本并保留主键与时间字段
  代码仓库       文件依赖、函数边界和语言语法           按模块、类或函数切分并保留路径

知识库不应只追求“导入成功”，还要保证解析后的内容适合检索和引用。

------------------------------------------------------------------------

## 5.2 文档处理

目标：

```text
非结构化文档
   ↓
解析正文与结构
   ↓
清洗和标准化
   ↓
形成文本、元数据和层级关系
```

处理内容：

-   清理噪声
-   保留标题层级
-   提取表格
-   添加 元数据（Metadata）
-   去除重复文档
-   识别语言、版本和更新时间
-   保留来源定位信息

元数据（Metadata） 示例：

```json
{
  "document_id": "deploy-guide-v2",
  "document": "deploy.pdf",
  "title": "生产环境部署规范",
  "section": "数据库变更",
  "page": 10,
  "version": "2.0",
  "department": "研发部",
  "permission": "team-a",
  "updated_at": "2026-08-01"
}
```

元数据可用于：

-   按部门、版本或产品范围过滤；
-   在回答中显示文件名和页码；
-   控制不同用户的访问权限；
-   文档更新时识别并删除旧版本切片；
-   分析某条答案来自哪一份资料。

文档处理完成后应抽样检查：正文是否完整、标题层级是否正确、表格是否错位、页码是否可追溯，以及敏感内容是否已按规则处理。

# 6. 文档切片（Chunk）

文档切片（Chunk） 是 RAG 效果最关键的工程环节之一。

## 6.1 为什么需要文档切片

原因：

-   上下文窗口（Context Window） 限制
-   降低 Token 成本
-   提升检索粒度
-   减少无关信息

如果把整份长文档作为一个检索单元，向量会混合多个主题，用户只问其中一个知识点时，检索结果不够精确。如果切片过碎，单个切片又可能缺少回答问题所需的上下文。

好的切片应该尽量满足：

-   一个切片围绕一个相对完整的主题；
-   读者只看该切片也能理解基本含义；
-   保留标题、章节和来源信息；
-   长度适合向量化模型和后续上下文窗口；
-   可以通过文档 ID、页码等信息定位回原文。

------------------------------------------------------------------------

## 6.2 文档切片的核心参数

### 切片大小（chunk_size）

`chunk_size` 表示单个切片允许包含的字符数或 Token 数。它没有适用于所有项目的固定最佳值，需要根据文档结构、问题类型和模型限制进行评测。

过大：

-   噪声增加
-   检索不精准

过小：

-   上下文不足
-   语义被拆散
-   相邻切片数量增加

例如，“故障原因”和“解决步骤”位于相邻段落时，如果切片过小，系统可能只召回原因而漏掉解决步骤。

------------------------------------------------------------------------

### 重叠长度（overlap）

`overlap` 表示相邻切片之间重复保留的内容，用于减少信息在边界处被截断的问题。

重叠过小可能丢失上下文；重叠过大会产生大量重复内容，增加向量存储、检索去重和模型 Token 成本。

参数调优不能只凭经验，应准备一批真实问题，比较不同组合下的 Recall@K、答案正确率和 Token 消耗。

------------------------------------------------------------------------

## 6.3 文档切片（Chunk）方法

### 固定长度切片（Fixed-Length Chunking）

固定长度切分。

优点：

-   简单

缺点：

-   容易破坏语义。

适合日志、短消息或结构不明显的文本。对技术文档直接按字符截断时，可能把一个步骤或表格拆开。

------------------------------------------------------------------------

### 滑动窗口切片（Sliding Window）

通过窗口重叠保留上下文：

```text
切片 1：A B C D E
切片 2：      D E F G H
```

优点是实现简单并能保留边界上下文；缺点是会产生重复内容，检索结果需要去重。

------------------------------------------------------------------------

### 递归切片（Recursive Chunking）

按照结构递归切分：

    标题
     ↓
    章节
     ↓
    段落
     ↓
    句子

适合技术文档。

递归切片优先按照标题、段落、句子等自然结构拆分，只有内容仍然过长时才继续向下切。相比固定长度切分，它更容易保持语义完整，是通用文档 RAG 的常见起点。

------------------------------------------------------------------------

### 语义切片（Semantic Chunking）

根据语义变化切分。

系统可以计算相邻句子或段落的语义相似度，在主题发生明显变化的位置切分。它适合段落结构较差但主题变化清晰的文本。

优点是语义边界更自然；缺点是需要额外的向量化或模型计算，处理成本更高，切片长度也可能不稳定。

------------------------------------------------------------------------

### 父子文档检索（Parent-Child Retrieval）

解决：

> 使用较小的子切片提高检索精度，再返回较大的父级内容帮助模型理解完整上下文。

```text
父级章节：数据库变更流程
   ├── 子切片：变更前备份
   ├── 子切片：执行变更脚本
   └── 子切片：失败后的回滚

检索子切片 → 找到“失败后的回滚” → 返回父级章节作为上下文
```

父子检索适合规章制度、技术手册和长章节文档，但需要维护父子 ID 映射，并控制返回父级内容的长度。

### 不同文档的切片建议

  文档类型     推荐方式                       注意事项
  ------------ ------------------------------ --------------------------------
  技术文档     递归切片或父子检索             保留标题、代码块和步骤顺序
  表格         按完整表格或逻辑行组切分       同时保留表头和单位
  代码         按模块、类或函数切分           保留文件路径、语言和调用关系
  FAQ          一个问题与答案作为一个切片     不要拆开问题和答案
  合同制度     按章节和条款切分               保留条款编号、版本和生效时间

面试中可以这样回答：

> 我不会只设置一个固定切片长度，而会先根据文档结构选择切片策略，再通过标注问题集比较 Recall@K 和最终答案质量。技术文档通常优先使用递归切片，并保留标题和元数据；需要兼顾精准检索与完整上下文时，会考虑父子检索。

------------------------------------------------------------------------

# 7. 向量化表示与向量数据库（Embedding & Vector Database）

## 7.1 向量化表示（Embedding）

向量化表示（Embedding） 将文本转换为向量：

    文本
     ↓
    向量化模型（Embedding Model）
     ↓
    Vector

语义相近文本在向量空间距离更近。

### 如何生成向量化表示

RAG 系统通常使用专门的向量化模型（Embedding Model）生成向量，而不是直接让大语言模型生成。

常见方式：

  方式                 实现方法                           特点与适用场景
  -------------------- ---------------------------------- ----------------------------------------
  云端模型接口         调用厂商提供的 Embedding API      接入简单、无需部署，适合快速开发和在线服务
  本地开源模型         部署 BGE、E5 等向量化模型         数据可留在本地，适合私有化和敏感数据场景
  批量离线向量化       对文档切片分批生成并保存向量       适合大规模知识库构建，可降低请求次数和成本

知识库构建阶段：

    文档切片
       ↓
    文本清洗与必要的标题补充
       ↓
    向量化模型
       ↓
    文档向量
       ↓
    写入向量数据库

用户查询阶段：

    用户问题
       ↓
    使用同一个向量化模型
       ↓
    查询向量
       ↓
    与文档向量计算相似度

需要注意：

-   文档和查询必须使用同一个向量化模型，否则二者不在同一向量空间中，无法正确比较；
-   两个阶段应使用一致的文本预处理和向量归一化规则；
-   模型选型需要考虑中文效果、向量维度、最大输入长度、推理速度、成本和私有化要求；
-   更换向量化模型后，通常需要重新生成全部文档向量并重建索引。

------------------------------------------------------------------------

## 7.2 相似度计算

相似度计算用于衡量查询向量与文档向量之间的接近程度。向量越相似，通常表示两段文本的语义越相关。

在检索阶段，系统会计算查询向量与知识库中各文档向量的相似程度，并按照得分返回最相关的前 K 个文档切片。

    查询向量
       ↓
    与文档向量计算相似度
       ↓
    按相关程度排序
       ↓
    返回 TopK 文档切片

### 余弦相似度（Cosine Similarity）

余弦相似度计算两个向量方向的接近程度，不重点关注向量本身的长度。

    cosine(A, B) = (A · B) / (|A| × |B|)

取值通常在 `-1` 到 `1` 之间：

-   越接近 `1`，表示方向越一致，语义通常越相似；
-   接近 `0`，表示相关性较弱；
-   越接近 `-1`，表示方向相反。

特点：

-   对向量长度不敏感；
-   适合比较文本的语义方向；
-   是文本向量检索中常见的计算方式。

### 点积（Dot Product）

点积将两个向量对应位置的数值相乘后求和：

    dot(A, B) = A1×B1 + A2×B2 + ... + An×Bn

点积越大，通常表示两个向量越相似。它同时受到向量方向和向量长度影响。

特点：

-   计算简单、速度快；
-   适合使用点积进行训练或优化的向量化模型；
-   如果向量已经归一化，点积与余弦相似度的排序结果通常一致。

### 欧氏距离（Euclidean Distance）

欧氏距离计算两个向量在空间中的直线距离：

    distance(A, B) = √((A1-B1)² + (A2-B2)² + ... + (An-Bn)²)

与前两种方法不同，欧氏距离的数值越小，表示两个向量越接近、语义越相似。

特点：

-   直观反映向量之间的空间距离；
-   同时受到方向和长度影响；
-   适合模型明确使用距离进行训练和比较的场景。

### 如何选择

  计算方式       判断相似的标准       主要特点                     常见场景
  -------------- -------------------- ---------------------------- --------------------------
  余弦相似度     得分越大越相似       关注方向，不关注向量长度     文本语义检索
  点积           得分越大越相似       计算快，受方向和长度影响     模型指定使用点积的场景
  欧氏距离       距离越小越相似       衡量向量空间中的直线距离     距离型向量检索

实际项目中不应随意选择计算方式，应优先遵循向量化模型的官方建议，并保证知识库构建和查询阶段使用相同的计算方式。

需要注意：相似度分数只表示向量之间的接近程度，不等于答案正确率。RAG 系统仍需要通过 Recall@K、MRR 等指标评估实际检索效果。

------------------------------------------------------------------------

## 7.3 向量数据库（Vector Database）

向量数据库用于存储文档向量，并根据查询向量快速找到语义相近的文档切片。

一条向量数据通常包含：

```json
{
  "id": "chunk_001",
  "vector": [0.12, -0.35, 0.86],
  "text": "生产环境部署前需要完成数据库备份。",
  "metadata": {
    "document": "部署规范.pdf",
    "section": "生产发布",
    "version": "3.0",
    "department": "研发部",
    "permission": "internal"
  }
}
```

核心能力：

### 向量存储（Vector Storage）

向量数据库将文档切片的向量、原始文本和元数据关联保存。向量用于检索，原始文本用于构建模型上下文，元数据用于过滤、权限控制和来源引用。

例如，系统导入《部署规范.pdf》时，会先将文档切片并生成向量，再把每个切片作为一条数据写入向量数据库。

### 相似搜索（Similarity Search）

用户问题也会通过同一个向量化模型转换为查询向量。向量数据库计算查询向量与文档向量的相似程度，并返回最相关的 TopK 结果。

例如，用户提问：

> 系统上线前需要做什么？

即使知识库中的原文是“生产环境部署前需要完成数据库备份”，两段文本没有使用完全相同的关键词，向量数据库仍可能根据语义相似性将其召回。

查询结果示例：

```text
Top1  生产环境部署前需要完成数据库备份。  相似度：0.91
Top2  发布前需要完成自动化测试。          相似度：0.84
Top3  发布失败后执行版本回滚。            相似度：0.72
```

### 元数据过滤（Metadata Filtering）

相似搜索可以与业务条件结合，只在满足条件的数据中进行检索。

例如，查询“支付系统如何部署”时，可以增加以下过滤条件：

```text
department = "支付研发部"
version = "3.0"
permission = "internal"
```

这样可以避免召回其他部门、旧版本或用户无权访问的文档。权限过滤应在检索阶段完成，不能先召回全部内容后再让大语言模型判断。

### 索引管理（Index Management）

当知识库包含大量向量时，逐条比较所有向量的成本很高。向量数据库会使用 HNSW、IVF 等索引缩小搜索范围，提高查询速度。

索引管理通常包括：

-   创建并选择合适的向量索引；
-   调整查询速度、召回率和内存占用之间的平衡；
-   在文档新增、更新或删除后同步维护索引；
-   更换向量化模型或向量维度后重建索引。

例如，一个包含千万条文档向量的知识库，可以通过近似最近邻索引快速筛选候选结果，再对候选向量进行更精确的相似度计算。

### 完整使用流程

```text
用户问题
   ↓
生成查询向量
   ↓
根据部门、版本和权限过滤数据
   ↓
通过向量索引执行相似搜索
   ↓
返回 TopK 文档切片及来源信息
   ↓
作为上下文交给大语言模型生成答案
```

------------------------------------------------------------------------

## 7.4 向量索引

向量索引用于加速相似搜索。如果知识库只有少量向量，可以逐条计算查询向量与所有文档向量的距离；当数据达到百万级或更大规模时，全量比较会带来较高的查询延迟。

```text
没有索引：查询向量 → 与全部向量逐一比较 → 排序 → TopK
使用索引：查询向量 → 快速定位候选区域 → 比较少量候选 → TopK
```

向量索引通常采用近似最近邻搜索（Approximate Nearest Neighbor，ANN）。它不保证每次都找到绝对精确的最近邻，而是在查询速度、召回率和资源占用之间取得平衡。

### 分层可导航小世界图（HNSW）

HNSW 将向量组织成多层图结构。查询时先在高层快速定位大致区域，再进入低层逐步寻找更接近的向量。

```text
查询向量
   ↓
高层图：快速定位相关区域
   ↓
低层图：搜索相邻节点
   ↓
返回距离最近的 TopK 向量
```

例如，一个企业知识库包含 500 万个文档切片。创建 HNSW 索引后，查询不需要扫描全部 500 万条向量，而是沿图结构访问一部分候选节点。

示意配置：

```yaml
index_type: HNSW
M: 16
ef_construction: 200
ef_search: 64
```

-   `M`：每个节点连接的邻居数量。数值较大通常能提高召回率，但会增加内存占用；
-   `ef_construction`：创建索引时搜索的候选范围。数值越大，索引质量通常越高，但构建更慢；
-   `ef_search`：查询时搜索的候选范围。数值越大，召回率通常越高，但查询延迟也会增加。

HNSW 适合低延迟、高召回率的在线检索，但图结构通常需要较多内存。

### 倒排文件索引（IVF）

IVF 先将向量聚类并划分到多个中心区域。查询时先找到与查询向量最接近的聚类，只搜索其中一部分向量。

```text
全部向量
   ↓
聚类为多个向量区域
   ↓
查询时选择最相关的若干区域
   ↓
在这些区域内搜索 TopK
```

例如，将 1,000 万个向量划分为 4,096 个聚类。查询时只搜索最接近的 16 个聚类，从而大幅减少需要比较的向量数量。

示意配置：

```yaml
index_type: IVF_FLAT
nlist: 4096
nprobe: 16
```

-   `nlist`：建立索引时划分的聚类数量；
-   `nprobe`：查询时搜索的聚类数量。数值越大，召回率通常越高，但查询速度会降低。

IVF 适合较大规模的数据集，但需要先训练聚类中心；数据分布发生较大变化时，可能需要重新训练或重建索引。

### 乘积量化（PQ）

PQ 是一种向量压缩方法。它将高维向量拆分为多个子向量，并使用较短的编码表示每个子向量，以减少内存和存储占用。

```text
原始高维向量
   ↓
拆分为多个子向量
   ↓
分别量化并生成短编码
   ↓
使用压缩编码进行近似距离计算
```

例如，亿级向量无法全部以原始浮点数形式放入内存时，可以使用 PQ 压缩向量。查询速度和存储效率会提升，但压缩会损失部分精度。

PQ 经常与 IVF 组合使用：

```yaml
index_type: IVF_PQ
nlist: 4096
nprobe: 16
subvectors: 32
bits_per_code: 8
```

系统先通过 IVF 定位相关聚类，再使用 PQ 压缩编码计算近似距离，适合数据量很大且内存有限的场景。

### 如何选择索引

  索引或技术       主要特点                       适用场景
  ---------------- ------------------------------ --------------------------------
  暴力搜索         结果精确，无索引构建成本       小规模数据、效果基准测试
  HNSW             查询快、召回率高、内存占用大   低延迟在线 RAG
  IVF              通过聚类缩小搜索范围           百万级及以上向量检索
  IVF + PQ         聚类检索并压缩向量             亿级数据或内存受限场景

实际使用时，需要通过评测数据调整索引参数，同时观察 Recall@K、查询延迟和内存占用。索引参数不能只追求速度，否则可能因为候选范围过小而漏掉正确文档。

## 7.5 向量数据库选型

不同向量数据库在部署方式、扩展能力、元数据过滤和运维成本上各有侧重。

  数据库     部署方式                         主要特点                                           适用场景
  ---------- -------------------------------- -------------------------------------------------- ----------------------------------------
  Milvus     Lite、单机或分布式部署           支持多种向量索引、混合检索和水平扩展，功能完整     大规模企业知识库、高并发向量检索
  Qdrant     开源自建或托管云服务             元数据过滤能力较强，支持稠密与稀疏向量及分布式部署 需要复杂业务过滤、权限或多租户隔离的 RAG
  pgvector   PostgreSQL 扩展                  向量与关系数据统一存储，支持 SQL、事务和关联查询    已有 PostgreSQL、中小规模或业务数据关联较多的系统
  Pinecone   全托管云服务                     无需自行维护集群，支持命名空间、元数据过滤和混合检索 希望快速上线并减少数据库运维工作的云端应用
  LanceDB    本地嵌入式或服务化使用           与数据分析生态结合方便，支持向量、标量和全文检索     本地应用、原型验证、数据分析和离线处理场景

### 选型时重点考虑

-   **数据规模**：向量数量、向量维度以及未来增长速度；
-   **检索需求**：是否需要混合检索、范围搜索、重排序或多向量字段；
-   **过滤能力**：是否需要按租户、部门、版本、权限等元数据进行复杂过滤；
-   **部署方式**：选择本地嵌入式、自建服务、分布式集群还是全托管云服务；
-   **现有技术栈**：已有 PostgreSQL 的系统使用 pgvector 可以减少额外组件；
-   **运维与成本**：综合考虑机器资源、备份、监控、扩容和云服务费用；
-   **安全合规**：敏感数据是否允许进入外部托管服务，以及是否支持所需的访问控制。

没有绝对最好的向量数据库。小规模项目应优先控制系统复杂度，大规模项目则需要重点评估水平扩展、可用性、检索性能和运维能力。最终应使用真实业务数据测试 Recall@K、P95 查询延迟、资源占用和总体成本后再确定选型。

# 8. 检索（Retrieval）

检索阶段的目标是：从知识库中找出可能包含答案的文档切片。检索质量决定了模型能够看到什么资料；如果正确知识没有被召回，后续重排序和大语言模型通常也无法补救。

## 8.1 稠密检索（Dense Retrieval）

稠密检索先把用户问题转换为查询向量，再通过相似度计算查找语义接近的文档向量。

```text
用户问题：“系统上线前要准备什么？”
   ↓
查询向量
   ↓
向量相似搜索
   ↓
召回：“生产发布前必须完成数据库备份和回滚演练”
```

优势：

-   能发现用词不同但含义相近的内容；
-   适合自然语言问题和同义表达；
-   可以跨越简单的关键词差异。

不足：

-   对错误码、产品型号、函数名等精确词可能不够敏感；
-   效果依赖向量化模型和文档切片质量；
-   相似度较高不代表内容一定能回答问题。

------------------------------------------------------------------------

## 8.2 稀疏检索（Sparse Retrieval）

稀疏检索主要根据词语在查询和文档中的出现情况计算相关性，典型算法是 BM25。

BM25 会综合考虑：

-   查询词是否出现在文档中；
-   词语在当前文档中的出现频率；
-   词语在整个语料库中的稀有程度；
-   文档长度对词频的影响。

适合：

-   API 名、函数名和类名；
-   错误码和日志片段；
-   产品型号、订单号和专有名词；
-   用户明确记得原文关键词的场景。

例如查询 `ERR_CONNECTION_1024` 时，关键词检索通常比纯语义检索更稳定，因为该错误码本身已经是精确标识。

------------------------------------------------------------------------

## 8.3 混合检索（Hybrid Search）

混合检索同时使用稠密检索和稀疏检索，再合并两组结果。它兼顾语义理解和关键词精确匹配。

```text
用户问题
   ├── 稠密检索：召回语义相近内容
   └── BM25：召回关键词匹配内容
              ↓
          结果融合
              ↓
          候选 TopK
```

常见融合方法是倒数排名融合（Reciprocal Rank Fusion，RRF）。RRF 主要依据结果在各检索列表中的排名进行合并，不要求两种检索分数具有相同范围。

```text
稠密检索：A、B、C
BM25：    C、D、A
融合后：  A、C、B、D
```

混合检索不是一定优于单一检索。需要使用真实问题集比较 Recall@K、MRR 和查询延迟，并调整两类检索的候选数量及融合权重。

------------------------------------------------------------------------

## 8.4 查询优化（Query Optimization）

### 查询改写（Query Rewrite）

查询改写用于补全模糊表达、消除指代或转换成更适合知识库检索的形式。

```text
原问题：它怎么部署？
结合对话改写：产品 A 3.0 如何部署到 Kubernetes？
```

改写时不能擅自改变用户意图。系统应保留原问题，并记录改写后的查询，方便评测和排查。

### 多查询（Multi Query）

多查询让模型从不同角度生成多个检索表达，分别召回后再合并结果。

```text
原问题：如何减少 RAG 幻觉？
查询 1：RAG 幻觉的原因
查询 2：如何约束模型基于上下文回答
查询 3：RAG 无答案拒答策略
```

它可以提升召回率，但会增加检索次数、延迟和去重成本。

### HyDE

HyDE（Hypothetical Document Embeddings）先让模型生成一段“假设答案”，再对假设答案进行向量化并检索相似文档。

它适合用户问题过短、问题语言与文档语言差异较大的场景。风险是模型生成的假设答案可能带偏检索，因此必须通过评测确认是否有效。

### 检索阶段的关键参数

-   `top_k`：初始召回的候选数量；
-   `score_threshold`：最低相关性阈值；
-   元数据过滤条件：部门、版本、权限、时间等；
-   混合检索权重或融合方法；
-   是否启用查询改写、多查询和重排序。

`top_k` 过小可能漏掉正确文档，过大会增加噪声和重排序成本。参数应通过离线评测和线上反馈确定。

------------------------------------------------------------------------

# 9. 重排序（Rerank）

检索器的主要目标是尽可能召回正确内容，重排序器的目标是对候选结果进行更精细的相关性判断。

```text
用户问题
   ↓
检索器快速召回 Top50
   ↓
重排序模型逐条判断问题与候选内容的相关性
   ↓
保留 Top5
   ↓
构建上下文
```

向量检索通常分别编码问题和文档，速度快但交互较少。常见的交叉编码器（Cross-Encoder）会同时读取问题和候选文档，判断更准确，但计算成本更高。因此生产系统通常采用“快速召回 + 精细重排”的两阶段结构。

示例：

```text
问题：Java 服务内存溢出后如何处理？

初始召回：
1. Java 内存参数说明
2. 服务故障应急流程
3. Java OOM 排查与堆转储步骤

重排序后：
1. Java OOM 排查与堆转储步骤
2. 服务故障应急流程
3. Java 内存参数说明
```

关键参数：

-   初始召回数量：决定重排序器能看到多少候选；
-   最终保留数量：决定交给模型的上下文规模；
-   最大输入长度：候选文档过长时可能被截断；
-   相关性阈值：低于阈值时可以拒答或再次检索。

重排序无法找回检索阶段完全漏掉的文档。因此优化顺序通常是先保证 Recall@K，再优化 MRR、NDCG 和最终上下文质量。

面试中可以这样回答：

> 检索器负责以较低成本扩大召回范围，重排序器负责提高候选结果的排序精度。我们通常先召回较多候选，再用交叉编码器保留少量高相关结果，并通过 Recall@K、MRR、延迟和成本共同确定候选数量。

------------------------------------------------------------------------

# 10. 上下文构建与答案生成

## 10.1 上下文管理（Context Management）

检索结果不能不经处理就全部拼接给模型。上下文构建需要在相关性、完整性和 Token 成本之间取得平衡。

主要处理：

-   **去重**：删除高度重复或来自重叠切片的内容；
-   **排序**：综合相关性、文档顺序、时间和来源可信度排列；
-   **扩展**：必要时补充相邻切片或父级章节；
-   **压缩**：去除与问题无关的句子，但保留关键证据；
-   **Token 控制**：为系统提示、问题、上下文和回答分别预留空间；
-   **来源映射**：每段上下文保留文档名、页码和切片 ID。

```text
TopK 候选
   ↓ 去重
相关文档切片
   ↓ 按来源和逻辑排序
可读上下文
   ↓ 按 Token 预算裁剪
最终输入模型的上下文
```

常见错误是只按相似度分数拼接内容，导致同一段重复出现、步骤顺序混乱，或最新制度与旧版本同时进入上下文。

------------------------------------------------------------------------

## 10.2 提示词约束（Prompt）

提示词应明确告诉模型如何使用检索资料，而不只是把资料放在问题前面。

```text
你是企业知识库助手。
请仅根据“参考资料”回答问题。
如果资料不足，请明确说明未找到可靠依据，不要猜测。
回答中的关键结论需要标注来源编号。

参考资料：
[1] ...
[2] ...

用户问题：...
```

提示词可以降低无依据生成，但不能替代高质量检索，也不能作为权限控制手段。

------------------------------------------------------------------------

## 10.3 来源引用（Citation）

引用可以提高答案的可解释性，让用户核验模型结论。常见引用信息包括：

-   文档名称和链接；
-   页码、章节或条款编号；
-   文档版本和更新时间；
-   对应的切片 ID。

引用必须与实际使用的上下文绑定，不能让模型凭空生成来源。更可靠的做法是由系统根据切片元数据生成引用编号，再让模型引用编号。

无答案场景也需要设计。若所有候选均低于阈值，系统应返回“知识库中没有找到足够可靠的信息”，并可以提示用户补充关键词或转人工处理。

------------------------------------------------------------------------

# 11. RAG 评测体系

RAG 不能只看最终回答是否“感觉不错”。完整评测应拆分为检索、生成和系统三个层次，这样才能判断问题发生在哪里。

## 11.1 检索评测（Retrieval Evaluation）

衡量是否找到正确知识。

指标：

### Recall@K

衡量正确文档是否出现在前 K 个检索结果中。

```text
10 个问题中，有 8 个问题的正确文档进入 Top5：
Recall@5 = 8 / 10 = 0.8
```

它适合判断检索器有没有把正确知识找出来，是 RAG 检索评测中最重要的基础指标之一。

### Precision@K

衡量前 K 个结果中相关文档所占比例。Precision@K 高，表示候选噪声较少。

例如 Top5 中只有 2 条真正相关，则 Precision@5 为 `2/5 = 0.4`。

### MRR

平均倒数排名（Mean Reciprocal Rank）关注第一个正确结果出现的位置。正确结果越靠前，得分越高。

第一个正确结果排第 1，倒数排名为 1；排第 2，得分为 1/2；排第 5，得分为 1/5。

### NDCG

归一化折损累计增益（NDCG）适合相关性不只是“正确或错误”，而是存在高度相关、部分相关和不相关等等级的场景。它会让排名靠前的高相关结果获得更大权重。

------------------------------------------------------------------------

## 11.2 生成评测（Generation Evaluation）

### Faithfulness

忠实度衡量回答中的结论是否能够从检索上下文中得到支持。答案可能读起来正确，但如果加入了上下文中不存在的内容，忠实度仍然较低。

### Answer Correctness

答案正确性衡量模型回答与标准答案或事实之间的一致程度。可以结合人工标注、规则判断或模型评审，但模型评审需要抽样校验。

### Answer Relevance

答案相关性衡量回答是否真正回应了用户问题。内容即使正确，如果大量偏离主题，相关性也会降低。

还应评估：

-   无答案问题是否正确拒答；
-   引用是否真实并支持对应结论；
-   答案是否完整覆盖问题中的多个要求；
-   是否泄露了用户无权访问的信息。

------------------------------------------------------------------------

## 11.3 评测数据集（Evaluation Dataset）

需要包含：

-   用户问题（Query）；
-   标准答案或关键得分点；
-   正确文档和正确切片；
-   问题类型、难度和权限标签；
-   是否应该拒答。

覆盖：

-   正常问题
-   模糊问题
-   无答案问题
-   越权问题
-   Prompt Injection

评测集应来自真实业务问题，而不只是根据文档自动生成的简单问题。需要包含同义表达、错别字、多轮指代、跨文档问题和知识库中不存在答案的问题。

## 11.4 系统评测（System Evaluation）

系统层关注能否稳定、经济地提供服务：

-   P50、P95、P99 查询延迟；
-   每次请求的 Token 和模型调用成本；
-   并发量、吞吐量和错误率；
-   向量索引占用的内存和存储；
-   缓存命中率与知识更新后的数据新鲜度。

一次优化只有在评测指标上稳定提升，才可以认为有效。不能只选择几个示例进行主观比较。

------------------------------------------------------------------------

# 12. RAG 问题定位与优化

## 12.1 TopK 分数低怎么办

相似度分数低不一定意味着向量数据库有问题。建议按照以下顺序排查：

1.  **知识覆盖**：知识库中是否真的存在答案，版本是否正确；
2.  **解析质量**：目标内容是否被正确提取，表格或扫描件是否解析失败；
3.  **切片质量**：答案是否被拆散，标题和关键上下文是否丢失；
4.  **向量化模型**：模型是否适合中文和当前领域，文档与查询是否使用同一模型；
5.  **查询表达**：问题是否过短、存在指代或专业缩写；
6.  **检索策略**：是否需要 BM25、混合检索、元数据过滤或多查询；
7.  **索引参数**：ANN 参数是否过度追求速度而降低召回。

策略：

-   设置经过评测的相关性阈值；
-   改写查询后重新检索；
-   切换或增加关键词检索；
-   放宽错误的元数据过滤条件；
-   知识库没有答案时明确拒答。

不能看到分数低就直接降低阈值。阈值过低会把无关资料交给模型，反而增加幻觉。

------------------------------------------------------------------------

## 12.2 回答错误如何定位

链路：

```text
原文是否正确
   ↓
解析结果是否完整
   ↓
正确切片是否进入 TopK
   ↓
重排序后是否仍被保留
   ↓
上下文是否完整且顺序正确
   ↓
提示词是否要求基于证据回答
   ↓
模型是否正确理解并生成
```

典型定位方法：

-   正确切片没进入 TopK：优先检查解析、切片和检索；
-   正确切片已召回但被重排序删除：检查重排序模型和候选长度；
-   正确上下文已经给模型但回答错误：检查上下文组织、提示词和模型能力；
-   答案正确但引用错误：检查切片 ID 与引用生成逻辑；
-   旧版本内容被召回：检查版本元数据、过滤和增量更新流程。

生产系统应保存查询、改写结果、过滤条件、召回列表、重排序得分、最终上下文和模型输出，形成可观测的排查链路。

------------------------------------------------------------------------

# 13. 生产级 RAG 工程化

能够完成问答演示不等于能够投入生产。生产级系统还需要处理性能、知识更新、权限、安全、监控和故障恢复。

## 13.1 性能优化

RAG 请求通常包含查询改写、向量化、检索、重排序和大语言模型生成等多个步骤。优化前应先记录各环节耗时，找到真正的瓶颈。

常见优化方法：

-   使用 ANN 索引加速大规模向量检索；
-   对重复问题、查询向量或最终答案使用缓存；
-   文档导入时批量生成向量，提高吞吐量；
-   稠密检索、BM25 和多知识库查询并行执行；
-   控制初始 TopK 和重排序候选数量；
-   减少重复上下文和不必要的模型 Token；
-   为外部模型调用设置超时、重试和降级策略。

关注：

-   端到端延迟及各阶段延迟；
-   P50、P95、P99，而不只是平均值；
-   每次请求的 Token 和模型成本；
-   峰值并发、吞吐量和失败率；
-   优化是否降低了 Recall@K 或答案质量。

例如，把 TopK 从 50 降到 10 可能降低重排序延迟，但也可能漏掉正确知识。性能优化必须同时检查质量指标。

------------------------------------------------------------------------

## 13.2 知识更新

完整流程：

```text
检测新增、修改或删除的文档
   ↓
解析并计算内容版本
   ↓
生成新切片和向量
   ↓
写入新版本数据
   ↓
切换生效版本
   ↓
删除或归档旧切片
```

需要：

-   **增量更新**：只处理发生变化的文档，避免全量重建；
-   **幂等性**：相同任务重复执行不能生成重复切片；
-   **版本管理**：记录文档版本、更新时间和切片版本；
-   **删除同步**：原文删除后，对应向量也必须删除；
-   **原子切换**：避免用户同时检索到新旧两个版本；
-   **回滚机制**：新索引异常时能够恢复到上一版本。

更换向量化模型或向量维度时，一般需要创建新索引并重新生成全部文档向量，验证完成后再切换流量。

------------------------------------------------------------------------

## 13.3 权限控制

企业 RAG 必须：

```text
用户身份与租户
   ↓
计算允许访问的部门、项目和文档范围
   ↓
将权限条件加入检索过滤
   ↓
只召回授权内容
```

不能：

```text
错误做法：召回全部机密资料 → 让模型决定哪些可以展示
```

权限控制应在检索之前或检索过程中执行。还需要防止缓存把一个用户的答案返回给另一个无权限用户，并在日志中避免记录敏感正文。

常见隔离方式：

-   按租户使用独立数据库、集合或命名空间；
-   在共享集合中使用租户 ID 和权限字段过滤；
-   对高敏感数据使用物理隔离；
-   对每次检索记录用户、过滤条件和访问来源，便于审计。

------------------------------------------------------------------------

## 13.4 Prompt Injection 防护

提示注入是指用户输入或被检索文档中包含恶意指令，试图让模型忽略系统规则、泄露数据或执行危险操作。

风险来源：

-   用户直接输入“忽略之前的规则”；
-   网页或文档中隐藏恶意指令；
-   被污染的知识库内容诱导模型调用工具；
-   模型在回答中泄露系统提示或机密资料。

防护措施：

-   明确区分系统指令、用户输入和检索资料；
-   将检索内容视为数据，而不是可执行指令；
-   导入知识库前进行来源校验、恶意内容检测和人工审核；
-   工具调用使用最小权限，并对高风险操作要求确认；
-   输出前进行敏感信息检测；
-   使用越权、注入和数据外泄测试集持续评测。

提示词本身不能提供完整安全保障，安全控制必须落实在权限、工具接口和数据层。

## 13.5 可观测性与监控

生产系统至少应记录：

-   原始查询与改写后的查询；
-   使用的知识库、过滤条件和索引版本；
-   TopK 候选、相似度和重排序得分；
-   最终进入模型的上下文及引用映射；
-   各阶段耗时、Token、成本和错误信息；
-   用户反馈、拒答率和无结果查询。

这些信息既用于故障排查，也用于发现知识缺口和构建新的评测样本。记录时需要脱敏，并设置合理的访问权限和保存周期。

------------------------------------------------------------------------

# 14. 高级 RAG 架构

高级 RAG 不是越复杂越好。只有基础 RAG 在评测中暴露出明确问题时，才应该引入更复杂的检索和决策流程。

## 14.1 智能体增强 RAG（Agentic RAG）

智能体根据问题动态决定：

-   是否检索
-   检索几次
-   使用哪个知识库

例如，用户询问故障时，智能体可以先检索运维手册；如果信息不足，再查询监控工具或工单系统。它适合路径不固定的复杂任务，但会增加调用次数、延迟和不可预测性。

------------------------------------------------------------------------

## 14.2 图 RAG（Graph RAG）

利用知识图谱解决：

-   实体关系
-   多跳推理

例如问题“系统 A 的负责人所在团队还维护哪些服务”，需要沿着“系统—负责人—团队—服务”的关系进行多跳查询。图 RAG 适合实体关系密集的场景，但知识图谱构建和维护成本较高。

------------------------------------------------------------------------

## 14.3 自反思 RAG（Self-RAG）

模型主动判断：

-   是否需要检索
-   回答是否可信

模型可以在生成过程中检查检索资料是否相关、回答是否有证据，并决定是否再次检索。它有助于改善复杂问题，但会增加模型调用和评测难度。

------------------------------------------------------------------------

## 14.4 纠错 RAG（Corrective RAG）

纠错 RAG 会先评估检索结果质量。如果结果不可靠，系统可以改写查询、切换知识源、扩大检索范围或使用外部搜索，再重新生成答案。

选择高级架构时，应先回答三个问题：基础系统的具体失败类型是什么、复杂方案能改善哪个指标、增加的延迟和成本是否可以接受。

------------------------------------------------------------------------

# 15. RAG 项目实践与面试

## 15.1 示例项目架构

```text
PDF、Word、Markdown、网页
   ↓
解析、清洗和元数据提取
   ↓
递归切片与父子关系
   ↓
批量生成向量
   ↓
向量数据库 + BM25 索引
   ↓
权限过滤与混合检索
   ↓
重排序
   ↓
上下文去重、排序和 Token 控制
   ↓
大语言模型生成
   ↓
答案、来源引用与无答案处理

评测集贯穿整个流程：
Recall@K、MRR、忠实度、正确性、延迟和成本
```

## 15.2 项目落地步骤

1.  明确用户、数据范围、问题类型和成功指标；
2.  选择一小批有代表性的文档完成基础流程；
3.  建立包含正确文档和标准答案的评测集；
4.  优化解析、切片和基础检索，先保证 Recall@K；
5.  加入混合检索和重排序，改善排名与上下文质量；
6.  完成拒答、引用、权限和知识更新；
7.  压测延迟、并发和成本；
8.  小流量上线并通过用户反馈持续迭代。

项目介绍不要只说“调用了向量数据库和大模型”，而要说明业务问题、数据特点、遇到的失败类型、采用的方案以及指标变化。

------------------------------------------------------------------------

## 15.3 面试重点

### 如何评估 RAG？

回答：

> 我会把 RAG 评测拆成检索、生成和系统三层。检索层使用标注了正确文档或切片的问题集，评估 Recall@K、Precision@K、MRR 和 NDCG；生成层评估答案正确性、相关性、忠实度和引用准确性；系统层关注 P95/P99 延迟、Token 成本、吞吐量和错误率。这样才能判断问题发生在检索还是生成阶段。

------------------------------------------------------------------------

### TopK 分数低怎么办？

回答：

> 我不会直接降低阈值。首先确认知识库中是否有答案，再检查解析和切片是否完整、向量化模型是否匹配、查询是否需要改写，以及元数据过滤和 ANN 参数是否正确。对于错误码和专有名词会加入 BM25 或混合检索。如果仍没有可靠结果，就明确拒答，避免把无关内容交给模型。

------------------------------------------------------------------------

### RAG 最大难点？

回答：

> RAG 最大的难点不是调用模型，而是把非结构化知识组织成可检索、可更新、可评测的系统。具体包括解析复杂文档、设计切片、保证召回质量、处理版本和权限，以及建立从检索到生成的评测闭环。

### 为什么需要重排序？

回答：

> 初始检索的目标是低成本地扩大召回范围，排序精度有限。重排序模型会同时分析问题和候选文档，以更高成本进行精细相关性判断。通常先召回较多候选，再重排保留少量结果。它能改善排名，但无法找回检索阶段完全漏掉的文档。

### 如何选择向量数据库？

回答：

> 我会从数据规模、过滤和权限需求、部署方式、现有技术栈、可用性、运维成本和安全合规几个方面评估。已有 PostgreSQL 且规模适中时可以优先考虑 pgvector；复杂过滤或独立向量服务可以评估 Qdrant；大规模分布式场景可以评估 Milvus；希望减少运维时可以考虑托管服务。最终需要用真实数据比较召回率、P95 延迟和成本。

### RAG 与微调有什么区别？

回答：

> RAG 主要在推理时提供外部知识，适合最新和私有资料；微调通过训练改变模型参数，更适合稳定的行为、风格和任务能力。两者可以组合使用，微调负责“怎么做”，RAG 负责“知道什么”。

## 15.4 小白学习顺序

建议按照以下顺序掌握：

1.  理解 RAG 的离线和在线流程；
2.  掌握文档解析、切片与元数据；
3.  理解向量化、相似度和向量索引；
4.  掌握稠密检索、BM25、混合检索和重排序；
5.  学会上下文构建、提示词约束、引用和拒答；
6.  使用 Recall@K、MRR、忠实度等指标评测；
7.  学习权限、更新、监控和安全；
8.  最后再理解智能体增强 RAG、图 RAG 等高级架构。

学习每个知识点时，都应能够回答四个问题：它解决什么问题、基本原理是什么、工程上如何使用、如何证明它有效。
